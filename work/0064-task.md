## Problem

The Agents page (0035) lets the user pin each role (engineer, reviewer, pm, custom) to a specific coding agent + model, and the freeform flow (0036) and Start-work flow (0037/0042) resolve those defaults at run time. But today those defaults are locked in for every task: the task's Agent tab gives no indication of *which* agent/model is running the task, and there is no way to run one task (or one freeform generation) with a different agent or model without editing the global defaults. 0036 explicitly deferred "per-task agent overrides" to a separate task — this is that task. The override must be granular and temporary: changing it for a task or a generation must never touch the defaults configured on the Agents page.

## Desired UX

### Task Agent tab (task drawer)

- At the top of the Agent tab, a readout shows the agent currently selected for this task, its coding agent, and its model — e.g. `engineer · opencode · big pickle` — pre-populated from the Agents page (or runtime defaults when none are configured).
- Compact controls next to the readout let the user change any of the three for *this task only*: an agent (role) select over all enabled agents, a coding-agent select (opencode / claude code / …), and a model select (default / big pickle / deepseek v4 / …).
- When an override is set, the readout is visibly distinct (e.g. a "custom" badge) and offers a reset-to-default control.
- The override drives Start work and follow-up messages for that task. A task with no override behaves exactly as today (uses the configured engineer agent).

### New task freeform pane

- Under the freeform textarea, a line shows the PM agent being used plus its coding agent and model — e.g. `PM agent: pm · opencode · big pickle` — pre-populated from the Agents page (or runtime defaults when none are configured).
- The same three controls let the user change the agent (any enabled agent; pm by default), its coding agent, and its model for *this freeform generation only*.
- The override is sent with that one freeform request and is not remembered for the next one.

### Shared rule

- Overriding in either place never writes to `repoos.toml` and never changes the Agents page defaults. The Agents page values are the fallback whenever no override is present.

## Acceptance criteria

- [ ] The task drawer's Agent tab shows the task's currently-selected agent, coding agent, and model, defaulting from the Agents page (engineer by default)
- [ ] The Agent tab's controls change the agent, coding agent, and model for that task only; the choice persists across drawer reopen and server restart
- [ ] Start work and follow-up messages honor the per-task override; with no override set they use the configured engineer agent exactly as today
- [ ] An overridden task is visually marked (e.g. "custom") and can be reset to the Agents page default
- [ ] The freeform pane shows the PM agent being used plus its coding agent and model, pre-populated from the Agents page
- [ ] The freeform pane's controls change the agent, coding agent, and model for that single generation; `POST /api/tasks/freeform` accepts and uses the override
- [ ] Freeform overrides are one-shot — the next generation defaults back to the configured PM agent
- [ ] The no-PM-agent and agent-failed fallbacks (raw explanation saved as a draft) still work unchanged
- [ ] Setting an override in either place never writes to `repoos.toml` and never changes the Agents page values on reload
- [ ] CLI/model combinations are validated using the same live model-source and
      compatibility rules as the Agents page; stale overrides fall back with a
      visible explanation rather than launching an invalid command
- [ ] `repoos check` passes

## Notes for AI

- **Where the defaults are resolved today**: `resolveEngineer` / `resolvePmAgent` in `src/server/agents.ts:241-251` pick the enabled agent from `config.agents`. `POST /api/tasks/freeform` (`src/server/server.ts:458`, `resolvePmAgent` at :485) runs the PM agent; `POST /api/tasks/:id/start` (:528, `resolveEngineer` at :537) and `POST /api/tasks/:id/message` (:612) resolve the engineer agent. `AgentRunner.start()` (`src/server/agents.ts:518`) and `runner.send()` take the resolved `Agent`. The override needs to slot into exactly these three resolution points.
- **Per-task override storage (assumption)**: persist the override in the task file frontmatter as optional keys (e.g. `agent_override`, `cli_override`, `model_override`). Unknown frontmatter keys are already preserved on write (`TaskFrontmatter` index signature + `Task.extra`, `src/core/types.ts:48-95`), so this is backward-compatible and survives restart, and both `start` and `message` can read it from the task. If you prefer a server-side per-task store instead, it must survive restart and be readable by the same two endpoints. State your choice in the implementation.
- **Agent shape**: an override is an `Agent`-like object `{ name, cli, model, enabled: true, instructions? }` (`src/core/types.ts:109`). When an override sets a different role, use that agent's own instructions; when only cli/model are overridden, keep the original agent's name and instructions.
- **UI targets**: the Agent tab and New task freeform pane both live in `src/ui-app/src/components/TaskDrawer.vue` (Agent session header + log ~:381-990; freeform pane ~:514-562; `createFreeformTask` in `src/ui-app/src/stores/repo.ts:265` sends the POST). Reuse the existing `Select` primitives and the model/CLI lists already exposed by `AgentsView.vue` (via `config.agentsMeta` + `/api/models`). The Agents page (`src/ui-app/src/views/AgentsView.vue`) must remain untouched by override flows.
- **Models are executable configuration now**: tasks 0083/0085 made model
  selection CLI-aware and forward explicit models to supported drivers. Resolve
  overrides through that existing command/model path; do not restore the old
  assumption that a model is merely a RepoOS display label.
- **Do NOT write config**: override flows must not use the `PATCH /api/config` write path. Only the Agents page itself may change `repoos.toml`. A malformed or stale override must degrade gracefully to the Agents page default, never crash the server.
- **Keep freeform fallbacks intact**: when no PM agent is configured or the agent call fails, the existing draft-fallback behavior (0036) must be preserved even when an override is present.

## Scope

- **This task**: agent/coding-agent/model readout + per-task override on the task Agent tab; agent/coding-agent/model one-shot override on the freeform pane; override-aware `freeform`, `start`, and `message` resolution; reset-to-default; no config writes.
- **Deferred**: per-task instruction overrides; per-task overrides for the reviewer or any other flow outside the task drawer and freeform pane.
