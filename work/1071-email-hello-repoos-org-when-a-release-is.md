## Problem
When a release goes out, the maintainer wants an email to hello@repoos.org with the release notes and any known issues, nicely formatted, so it can be forwarded to other users. Today the only signals are the in-app bell notice and the GitHub Release.

## Desired UX
Shortly after a stable release is actually downloadable (GitHub Release created and npm publish finished), one email arrives at hello@repoos.org: subject "RepoOS v<x> is out", an HTML body (plain-text alternative included) with the version, date, release notes grouped sensibly, links (GitHub release, changelog, upgrade command `repoos upgrade`), and a "Known issues" section. Prereleases (beta/canary/rc) do not email unless explicitly enabled.

## Design note (why not a git hook)
A local git hook is the wrong trigger: git has no post-tag-push or post-release hook, and a local hook would fire when the tag is pushed, which is BEFORE CI has built and published anything, so the email could announce a version that is not downloadable yet. The correct trigger is the last step of `.github/workflows/release.yml`, after the GitHub Release and npm publish steps succeed. RepoOS core stays free of any mail client (zero runtime dependencies, no secrets in repoos.toml).

## Acceptance criteria
1. A final job/step in `.github/workflows/release.yml` (needs: the publish steps; runs only on success and only for non-prerelease tags by default) sends the email using a transactional email HTTP API called with curl, or an Action pinned by SHA. No new runtime dependency in RepoOS.
2. Provider, sender address and the recipient come from GitHub repository secrets/variables (for example `RELEASE_EMAIL_API_KEY`, `RELEASE_EMAIL_FROM`, `RELEASE_EMAIL_TO` defaulting to hello@repoos.org). Never put a key or its env-var name in repoos.toml or in chat; the human adds the secret in GitHub settings (docs/api-keys.md rules apply). The step skips with a clear log line, and does NOT fail the release, when the secret is not set.
3. The body is generated by a script (`scripts/release-email.ts`, bun) from the release record: `release-history.json` entry (version, date, notes) and the "Known issues" source below. It renders both HTML and plain text; has a `--dry-run` that prints the email to stdout and writes an `.html` preview file; unit-tested with fixtures (escaping, empty notes, no known issues).
4. Known issues: the script reads open items from a `known-issues` list. Decide the source in the task (recommended: `docs/known-issues.md` or a section in `release-history.json` entry written at release time, editable in the release modal's notes). It must never invent issues; if none are recorded the section says "None recorded".
5. If the send fails, the workflow step reports the failure clearly but the release stays published; document how to resend (`gh workflow run` or a `workflow_dispatch` input with a tag).
6. Document in `docs/releases.md` and `user-docs` (what it does, which secrets to add, how to preview with --dry-run). Add a note for the human: they must create the email provider account and add the secrets themselves.
7. Surface the setting if user-facing: if there is any `repoos.toml` option (for example enabling the email), add it to the Settings UI per AGENTS.md; prefer no repoos.toml option at all.

## Notes for AI
Do not send any real email from tests or from the task run. Do not add credentials anywhere. Do not edit repoos.toml. Look at `.github/workflows/release.yml`, `docs/releases.md`, `src/server/release.ts` (release notes and changelog generation) and `release-history.json` for the data.
