Now that RepoOS has joined the Apple Developer Program, provision the credentials required for automated Developer ID signing and notarization of RepoOS Hub. This is a one-time maintainer operation: it requires access to the Apple Developer account, a maintainer-controlled private key, and repository administration rights. The implementation work in this slice is limited to documenting the credential contract and rotation runbook; the actual certificate creation and GitHub secret entry must be completed by an authorized human.

## Problem

RepoOS Hub's current release artifact is ad-hoc signed and not notarized, so macOS may show a Gatekeeper warning when a user first opens a downloaded app. The signing pipeline in #0577, #0578, and #0579 cannot be exercised end-to-end until CI has access to a valid Developer ID Application identity and a notarization credential. Those credentials cannot safely be generated by an agent: the certificate's private key must be controlled by a maintainer, and the Apple Developer portal and GitHub repository secrets require authorized human access. This task establishes the exact secret names and documents how to provision and rotate them without putting credential values in the repository.

## Desired UX

There is no UI change in this task; maintainers can provision and rotate the release credentials using the documented secret names and runbook, without per-release portal or Keychain work.

## Acceptance criteria

- [ ] An authorized maintainer creates or exports a valid **Developer ID Application** certificate and its matching private key as a password-protected `.p12`; the certificate is visible in the team's Apple Developer account and the exported identity can be imported on a macOS runner.
- [ ] The maintainer chooses and provisions one supported `notarytool` authentication method: preferred when no API key is already available, `APPLE_ID` plus `APPLE_APP_SPECIFIC_PASSWORD`; or the App Store Connect API-key set `APPLE_API_KEY`, `APPLE_API_KEY_ID`, and `APPLE_API_ISSUER_ID`. The chosen method is named in the runbook; secret values are never included there.
- [ ] GitHub Actions repository secrets exist with these exact names: `MACOS_CERTIFICATE` (base64-encoded `.p12` bytes, without line wrapping), `MACOS_CERTIFICATE_PASSWORD` (the `.p12` export password), and `APPLE_TEAM_ID` (the 10-character Apple Developer team identifier), together with exactly the selected notarization credential set above. For the API-key option, `APPLE_API_KEY` holds the private-key contents; any temporary `.p8` path needed by a workflow is generated at runtime and is not itself a repository secret.
- [ ] `docs/macos-hub-release.md` explains each secret's purpose, where to create the corresponding Apple credential, where to enter repository secrets in GitHub, which notarization method is provisioned, and how to rotate both certificate and notarization credentials step by step, including re-verification.
- [ ] Rotation guidance says to create and verify replacement credentials before revoking the old credential where Apple permits overlap, update the related secrets together, run a non-publishing signing/notarization verification once the dependent workflow tasks are available, and securely remove temporary credential files. It also notes that rotating a certificate does not invalidate already-notarized releases.
- [ ] No certificate, private key, `.p12`/`.p8` file, password, API key, or encoded credential value is committed, added to task text, or printed in CI logs. Only secret names and the selected authentication method may be documented.
- [ ] The release-workflow tasks #0577, #0578, and #0579 can consume the secret names and credential format defined here without inventing or renaming secrets. This task does not modify `.github/workflows/macos-hub.yml`.

## What to do

1. An authorized maintainer creates a Developer ID Application certificate in Certificates, Identifiers & Profiles using a maintainer-controlled key/CSR, imports the certificate and private key into Keychain Access, and exports the identity as a password-protected `.p12`. Confirm the certificate is associated with the RepoOS team and record its expiry date in the maintainer's secure credential inventory, not in this repository.
2. Create the notarization credential using the selected path: generate an app-specific password for the Apple ID, or create an App Store Connect API key and securely retain its `.p8` private key, Key ID, and Issuer ID. Do not put the private key in source control.
3. In the GitHub repository's **Settings → Secrets and variables → Actions**, create/update the exact secrets in the acceptance criteria. Base64-encode the `.p12` as a single line for `MACOS_CERTIFICATE`; never paste a raw file path or local credential into task text, logs, or a committed file. Use GitHub's secret input or another approved secure channel, not a command-line argument that exposes a value in shell history or process listings.
4. Update `docs/macos-hub-release.md` with the chosen authentication variant, a description of each secret, concise portal/export and GitHub secret-entry steps, and separate certificate and notarization-credential rotation procedures. Keep all values out of the document.
5. Once #0577–#0579 provide the pipeline, verify the configured credential names via repository secret metadata (names only) and run the documented non-publishing signing/notarization check. Confirm successful signing and notarization without exposing credential values; do not create a production release as a provisioning test.

## Notes for AI

- Apple Developer portal access, private-key export, Apple ID/API-key creation, and GitHub repository secret writes are human-only actions. Do not fabricate credentials, attempt to retrieve secret values, or claim these acceptance criteria are complete based only on documentation. If authorized access or confirmation is unavailable, finish only the documentation portion and report that human provisioning remains outstanding; use RepoOS's normal needs-input path if the task is being actively executed and is blocked.
- Never ask a maintainer to paste a certificate, private key, password, API key, or base64 credential into chat, a task, a commit, or a log. Record only whether provisioning is complete and which authentication method is in use.
- `APPLE_TEAM_ID` is available in Apple Developer account Membership details. `MACOS_CERTIFICATE` must be base64 of the export containing the matching private key, not merely the public `.cer` certificate.
- Unless an App Store Connect API key is already available, use the Apple ID/app-specific-password option. If the API-key option is selected, keep the secret names aligned with #0579; the workflow should materialize `APPLE_API_KEY` into a temporary `.p8` file at runtime and clean it up. Do not add `APPLE_API_KEY_PATH` as a separately provisioned secret.
- Keep this slice to credential provisioning and `docs/macos-hub-release.md`. Do not change the signing/notarization workflow or Xcode settings, which belong to #0577–#0579.
- Rotate before certificate or API-key expiry. Create and verify replacements before revoking the old credential when possible; changing a certificate does not invalidate releases that have already been notarized.
