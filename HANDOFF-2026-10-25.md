## 1. The one thing that matters: the RepoOS server keeps freezing

Symptom: `curl http://127.0.0.1:7171/api/health` times out (port listening, process at 0-5% CPU, state S). UI will not load, every
`repoos ...` CLI call takes 30-90 s. It happens even when the machine is idle (load ~10) and right after a fresh start (it answers
once, then stalls ~10 s later). Restarting does NOT cure it by itself.

Root cause (strong evidence): the server runs SYNCHRONOUS git spawns on its single main thread (git() in src/core/git.ts uses
execFileSync, 4 s timeout). On this Mac every process spawn is slow (macOS syspolicyd), the repo has 27 worktrees, 960 tasks and
22k commits touching work/, and RepoOS bookkeeping commits touch task files constantly. Found and fixed so far (both on main):
  - c916a3a4c  applyFileChange (src/server/live-index.ts) ran 3-4 sync git calls PER task-file change; now reuses prior git info
    when the branch is unchanged.
  - 2440b6985  lastCommitsForDir(Async) (src/core/git.ts): the `git log --name-only -- work` full walk took ~5 s (> the 4 s timeout,
    so it was killed and returned nothing on every refresh); now cached against HEAD + incremental (+ 120 s timeout for the first walk).
STILL OPEN, the next suspect, observed live while the server was hung:
  - `branchAheadCounts()` at src/core/git.ts:~231-250, called at git.ts:~1017 from the worktree-status reconcile. It runs
    `git for-each-ref --format=%(refname:short) %(ahead-behind:main) refs/heads/` through the SYNC git() helper. The child showed
    63% CPU for seconds, repeatedly, while the server did not answer. ahead-behind over ~100 branches on a 20k+-commit history is
    expensive, and the sync helper blocks the event loop for up to 4 s per call; reconcile/sweep timers repeat it.
  - Also sync and per-task: worktreeStatus() (git status --porcelain + git rev-list) used by src/server/task-watchdog.ts:323 and
    src/core/indexer.ts:104; `lastCommitForFile` and `worktreePaths` in applyFileChange's NEW-task branch.

## 2. How to restart the server safely

launchd owns the server (label com.repoos.serve.repoos-c4114ede, KeepAlive, 10 s throttle). NEVER run `just restart` while it is loaded
(starts a second server that fights launchd). If the server is hung: `kill -9 $(lsof -nP -tiTCP:7171 -sTCP:LISTEN)` and launchd starts a
fresh one in about 20-70 s (or `launchctl kickstart -k gui/$(id -u)/com.repoos.serve.repoos-c4114ede`; kickstart did NOT always kill a
hung instance, use kill -9 by pid when the port holder is older than the new process). After EVERY server start run `just clear`:
every RepoOS server (including preview/shot servers started from a task worktree) re-enables core.fsmonitor + untrackedCache in the
shared .git/config, which respawns ~30 git file-watcher daemons and hammers fseventsd. `just clear` (justfile, committed? see below)
turns it off in every repo under ~/code. Bug #0958 is the permanent fix (not landed).
