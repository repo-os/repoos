### Detail for #33 (cost estimate): root cause and suggested fix (from reading the RepoOS source)
- `estimateCostUsd(tokens)` (`src/server/agents.ts:539`) = `tokens x $9 / 1M` (the average of Claude 3.5 Sonnet's $3 input and $15 output) and is applied whenever a session has `totalTokens` but no reported cost (call sites `agents.ts:4405`, `agents.ts:6774`, `review.ts:127`).
- `totalTokens` includes cache-read tokens. For a cheap, heavily cached model (DeepSeek V4.1 Flash: ~$0.14/M input, ~$0.014/M cached) 2.8M tokens is real cost of a few cents; the estimate says $25, about 1,000x too high. It fires exactly when a run is cut off before usage is extracted (here: OpenRouter 402).
- Suggested fix: (1) never estimate from `totalTokens`; record cost as unknown (`null`, source `none`) when the CLI reported nothing, or price by model with separate input/cached/output rates; (2) exclude `estimate` rows from board totals and any guardrail, and show them as 'unknown' in the Tokens tab; (3) add a sanity cap (an estimate above N x the same model's median per-session cost is dropped); (4) test with a cached-heavy session.
- opex-side mitigation until fixed: spend checks use only `costSource = extractUsage` (real $3.87 at this point) and treat `estimate` as unknown. The single poisoned row ($25.29, task 0023) is in the local, gitignored `.repoos/repoos.db` `sessions` table; I have not edited it (owner decides).

### #36 verification (2026-10-05, owner asked me to double-check)
- Source: `src/commands/init.ts` chooses the starter task by CODE PATH, not by repo contents. The guided new-project flow (only reachable outside a git repo, needs a TTY) calls `scaffoldInto(..., "new")` and seeds "Flesh out the product vision". Any `repoos init` inside an existing git repo (line ~1462) always calls `scaffoldInto(..., "existing")` and seeds "Read this codebase".
- Reproduced in throwaway repos: (A) `git init` with no commits and (B) `git init` plus an empty commit both seeded `0002-read-the-codebase` as `status: ready`. (C) a non-git directory refuses headless init ("needs interactive prompts"). So an agent that cannot use a TTY cannot get the new-project starter at all.
- Verdict: matches the documented design (git repo = existing codebase), but it is a real usability gap for new projects bootstrapped headlessly, and the `ready` status makes the wrong starter dangerous with auto-engineering. Not a regression.
- **Owner decision (agreed): seed starter tasks as `inbox` or `draft`, never `ready`, so nothing auto-starts them.** Also agreed to keep the content-detection idea (empty repo -> vision task).
- **Owner decision (agreed): mark seeded tasks `created_by: repoos-init`** (today they say `created_by: human`), so they can be identified and auto-archived once the real backlog exists (ties in with the Archive task feature, RepoOS task 0657).

### Correction to #1 and #36 (2026-10-05, owner asked "couldn't an agent do the interactive init like a human?")
- I overstated #1 ("impossible for an agent"). But the guided new-project flow DOES work when driven through a pseudo-terminal (`python3 pty.fork()`, answering with Enter): prompts are (1) create in a new subdirectory [Y/n], (2) project description (optional), (3) task areas (optional), (4) make an initial commit [Y/n], (5) launch the web console [Y/n]. I did not try this when I started; I took the documented `git init` fallback instead and got the wrong starter task.
