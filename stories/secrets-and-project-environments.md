# Secrets and project environments

## Problem and outcome
RepoOS users need one place to configure project credentials without pasting values into tasks, chat, tracked configuration, or agent prompts. Add a Secrets sidebar page, initially between Dev and Agents, that shows what is set, missing, inherited, and used by which processes. Support separate named environments such as dev, integration, staging, production, dev-nick, and dev-alice; a repository and a developer machine may host several independent secret sets.

Source: Nick's request in the RepoOS chat on 2026-10-22. Reference screenshot: Screenshot 2026-10-22 at 15.55.14.png shows the existing sidebar (Control, Inputs, Work, Stories, Checks, Releases, Deployments, Dev, Agents, Context, Settings); preserve that visual language. No implementation tasks are created by this story; the slices below are proposed for refinement.

## Environment model
A named environment is an explicit configuration scope, not a Git branch, worktree, filename, or NODE_ENV value. Names are user-defined. A dev target, preview, check run, or deployment selects an environment explicitly. Switching the Secrets page selector changes only the view, never running processes or deployment destinations. Existing projects retain current behavior until they opt into named sets.

Example: dev-nick and dev-alice each define DATABASE_URL and STRIPE_SECRET_KEY with different values; integration uses a shared test database; production uses production credentials. Two dev targets may run concurrently against different environments without cross-contamination. Branches/worktrees do not automatically inherit production access. Worktree-local overrides, if supported, are explicit, temporary, and visible.

Keep project application secrets distinct from RepoOS's own provider/auth/infrastructure credentials. Existing fixed provider key names and dedicated save routes remain governed by docs/api-keys.md. A project-selected DATABASE_URL must not overwrite the RepoOS server's global process environment.

Start with explicitly registered file-backed sources: repo-root .env for legacy projects, and deliberate mappings for additional files such as apps/api/.env.local or .env.integration. Do not recursively merge every .env* file, infer environment from a filename, or treat NODE_ENV as an arbitrary environment selector. .env.example supplies expected key names and missing-key status, never real secret values. Different services can have different source mappings. Define and show precedence, duplicate-key errors, inherited source, and the effective configuration for each target. Machine/service values are read-only in the UI and do not silently override an explicitly selected project environment. Existing root-.env loading precedence is preserved in legacy mode.

Environment labels are not isolation by themselves: separate credentials, resource permissions, and controlled process injection provide the boundary. Sharing or cloning an environment defaults to names/placeholders only; copying values is an explicit privileged operation. Deployment environment changes never automatically upload secrets to an external provider.

## Secrets page
Environment selector; searchable rows showing key name, Set/Missing/Inherited status, source, visibility (server-only or public), consumers, and restart-needed state. Add, replace, and remove entries through masked inputs with explicit Save. Removal identifies affected consumers and requests confirmation. Detect external file edits and prevent stale concurrent writes. Preserve comments and unrelated entries with atomic, permission-restricted writes; refuse tracked secret destinations and unsafe paths/symlinks. Do not promise dotenv dialect support that the current minimal parser does not provide: support round-trip quoting deliberately, reject unsupported constructs clearly, and test fake values containing spaces, quotes, equals signs, and hash characters. Multiline values require an explicit later design rather than corrupting a file.

A selected environment can be created empty or from an example schema. Its page explains which local processes and deployment bindings use it. Production receives a prominent label and explicit selection; it is never a fallback for missing development keys. Non-secret environment metadata and key-name contracts may be committed; values never enter repoos.toml or other tracked files.

## Security contract and limits
Existing values are write-only in v1: metadata APIs return names/status/source only, never plaintext or recoverable masked values. Values entered for Save necessarily pass from the browser to the authenticated server over the protected connection, then are cleared from UI state. No reveal/copy-existing-value API in v1. Authenticated, authorized routes; CSRF/origin protection; no-store responses; no value-bearing logs, analytics, SSE events, errors, support bundles, task transcripts, or screenshots. Audit actor, environment, key name, action, and time without values. Use fake secrets in tests and screenshot fixtures.

Plaintext file backing is compatibility storage, not an encrypted vault. Gitignore does not prevent an agent or application with filesystem/process access from reading a secret. Document this boundary honestly. Processes receive only the selected environment's required values; managed agents, worktrees, and remote validation do not receive all project secrets by default. Explicit exposure policy must state what is enforced and what remains possible for unrestricted local agents. Redaction is defense in depth, not containment. Detect framework-public prefixes (such as VITE_ and NEXT_PUBLIC_) and prevent presenting client-exposed values as private credentials.

Reuse existing secret-handling primitives where appropriate, but do not expand setDotEnvSecret's global process.env mutation into arbitrary application keys. Evaluate the existing encrypted credential store as a later backend; keep encryption keys outside project worktrees and define key loss, rotation, recovery, and migration before claiming encryption-at-rest support. Do not migrate existing credentials silently.

## Proposed implementation tasks

1. Environment contract and storage foundation (core/server/docs). Decide environment IDs, source mappings, precedence, legacy compatibility, application-versus-RepoOS credential boundaries, and allowed consumers in an ADR. Implement validated metadata and robust file-backed read/write primitives. Tests: isolated env sets, safe paths, tracked-file refusal, round trips, atomic/concurrent edits, and unchanged legacy loading. No runtime dependency without explicit authorization. This is the foundation for every other slice.
2. Secret management API and access policy (server/CLI), depends on 1. Authenticated metadata listing and explicit add/replace/delete; role checks, origin protection, no-store, secret-safe error handling and audit trail. CLI lists metadata and accepts values via stdin/interactive input, avoiding command-line arguments. Tests use unique fake sentinel values and prove responses/logs/events never contain them. Reserve internal RepoOS names from arbitrary project overrides.
3. Secrets sidebar page (web), depends on 2. Environment selector, sources/status/consumers, expected names from examples, masked Save, replace/remove, and concurrent-edit feedback using existing shared components. Include a working empty state and environment creation. Declare shots with populated fake fixtures, light/dark/mobile views, dialogs, missing/inherited state; open every PNG. No real-secret screenshots. Update Settings schema for user-facing configuration and document any deliberate TOML-only structural rows.
4. Environment selection and scoped process injection (dev/previews/checks), depends on 1 and 2. Bind targets/runs to an environment, build a per-child env without mutating global process.env, apply explicit per-consumer grants, show restart requirements, and preserve legacy worktree inheritEnv behavior when unconfigured. Tests run two targets in different environments concurrently and prove no crossover; verify production is never a fallback and remote jobs receive no ungranted secrets. Expose resulting consumer state to slice 3.
5. Deployment bindings and production controls, depends on 3 and 4. Select and display an environment on a deployment; distinguish local run injection from provider-managed variables. Add provider integrations only with a supported explicit publish/sync operation, clear diff of key names and destination, and authorized human action. Tests use fake adapters and verify destination/scope, deletion behavior, and no accidental production propagation. External-account verification belongs in separately identified human work if required.
6. Security acceptance and user documentation, depends on 2 through 5. Exercise role denial, CSRF, cache behavior, value leakage through errors/logs/SSE/support bundles, tracked files, agent/worktree/remote access boundaries, and missing secrets. Update docs/api-keys.md, user-docs/environment-and-secrets.md, configuration docs, and directly affected AGENTS.md rules consistently. Each implementing slice still owns its tests, docs, and repoos check; this slice verifies integration rather than deferring safeguards until the end.

Suggested delivery: 1-4 form the first useful local release. Keep 5 as the next increment; 6 verifies each released scope. Reveal/copy, external vault backends, encrypted project storage, automatic provider sync, and sharing production values remain separate follow-ups requiring their own design.

## Story acceptance
A user can manage dev-nick, dev-alice, integration, and production sets from Secrets; replace/remove values without reading them back; see missing expected names and effective sources; bind two local targets to distinct sets without leakage; and understand where file-backed protection ends. Existing provider-key flows and projects without named environments keep working. Production credentials are neither inherited nor published implicitly.
